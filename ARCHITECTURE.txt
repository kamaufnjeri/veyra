# 8. Output/container settings should be separate from encoding

This is another important distinction.

For example:

```text
MKV → MP4
```

isn't simply "change codec."

We need to represent:

```python
@dataclass(frozen=True, slots=True)
class OutputSettings:
    format: str | None = None
    extension: str | None = None
```

Then:

```python
ConversionSettings(
    output=OutputSettings(format="mp4"),
    encode=EncodeOptions(
        video_codec="libx264",
        audio_codec="aac",
    ),
)
```

That makes the architecture understand:

```text
Container
    ↓
Video codec
    ↓
Audio codec
    ↓
Subtitle codec
```

as separate concerns.

# 11. Processor becomes job-based

Rather than making the processor interpret every possible GUI argument, we'll eventually give it normalized jobs:

```python
@dataclass(frozen=True, slots=True)
class OperationJob:
    operation: str
    inputs: tuple[Path, ...]
    output: Path | None
    settings: object
```

Then:

```text
GUI
 ↓
Workspace
 ↓
Planner
 ↓
OperationJob
 ↓
Processor
```

The processor doesn't need to know whether the GUI had a combo box called `"codec"`.

It receives:

```python
ConversionSettings(...)
```

and executes it.

# 12. Settings validation belongs in the backend

This is important too.

The GUI can prevent bad values, but **the backend must not trust the GUI**.

For example:

```python
ConversionSettings(
    crf=999,
    width=-100,
    fps=-4,
)
```

must fail before FFmpeg runs.

Likewise:

```text
MP4 + incompatible subtitle codec
MP3 extension + AAC codec
negative trim start
end <= start
invalid stream index
missing subtitle
missing media
same input/output
```

should all be validated by backend settings/operation validators.
