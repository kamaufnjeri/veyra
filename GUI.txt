# VEYRA — MEDIA WORKSPACE BLUEPRINT

## 1. Core UX principle

Veyra follows one simple workflow:

```text
ADD MEDIA
    ↓
FFPROBE INSPECTION
    ↓
MEDIA LIBRARY
    ↓
CLICK MEDIA
    ↓
VIEW ITS INFORMATION
    ↓
CHOOSE OPERATION
    ↓
SELECT MEDIA FOR THAT OPERATION
    ↓
CONFIGURE OPERATION
    ↓
VALIDATE
    ↓
RUN
    ↓
PROGRESS
    ↓
RESULTS
```

The workspace is divided into **four functional quadrants**:

```text
┌─────────────────────────────────┬─────────────────────────────────────┐
│                                 │                                     │
│       MEDIA LIBRARY              │       SELECTED MEDIA               │
│                                 │                                     │
│       TOP LEFT                  │       TOP RIGHT                     │
│                                 │                                     │
├─────────────────────────────────┼─────────────────────────────────────┤
│                                 │                                     │
│       OPERATIONS                │       OPERATION SETTINGS             │
│                                 │                                     │
│       BOTTOM LEFT               │       BOTTOM RIGHT                  │
│                                 │                                     │
└─────────────────────────────────┴─────────────────────────────────────┘
```

This separation should remain consistent throughout the application.

# 3. MEDIA LIBRARY

The Media Library is the **persistent workspace collection**.

Adding media does **not** mean selecting it for an operation.

## Controls

```text
[ + ADD MEDIA ] [ + ADD FOLDER ]
```

### Add Media

Opens a multi-file picker.

Supported examples:

```text
.mp4
.mkv
.mov
.avi
.webm
.ts
.m2ts
.m4v
.flv
.wmv
```

The architecture should allow additional formats later.

### Add Folder

Allows selecting a directory.

Veyra recursively discovers supported media files.

Potential option:

```text
☑ Include subfolders
```

# 4. Media Library item

Each media item should contain:

```text
┌────────────────────────────────────┐
│ ● Episode 01.mkv                   │
│   45:22 • 1.24 GB                  │
│   H.264 • 1920×1080                │
└────────────────────────────────────┘
```

The selected item gets a visually obvious state.

```text
● Episode 01.mkv
```

Unselected:

```text
  Episode 02.mkv
```

Clicking it changes:

```text
current_media
```

It does **not** change:

```text
operation_selected_media
```

# 5. FFprobe inspection

Every imported media file should automatically go through inspection.

```text
ADD FILE
   ↓
Validate path
   ↓
FFprobe
   ↓
Parse JSON
   ↓
MediaMetadata
   ↓
Store in workspace
```

The internal representation should contain information such as:

```python
MediaItem
├── id
├── path
├── filename
├── extension
├── size
├── duration
├── format
│
├── video_streams
│   ├── codec
│   ├── width
│   ├── height
│   ├── fps
│   ├── bitrate
│   ├── pixel_format
│   └── ...
│
├── audio_streams
│   ├── index
│   ├── codec
│   ├── language
│   ├── channels
│   ├── sample_rate
│   ├── bitrate
│   └── ...
│
└── subtitle_streams
    ├── index
    ├── codec
    ├── language
    ├── title
    ├── default
    └── forced
```

The UI should never need to independently run FFprobe just to display information.

There should be two different concepts.

### Clear subtitles

Only affects the selected media's subtitle configuration.


Removes all imported media from the workspace.

```text
CLEAR ALL
```

It should ask for confirmation if media have active operations.

# 19. Operation validation

Before allowing Run, Veyra validates the operation.

For example:

```text
✓ Media exists
✓ Media inspected
✓ Operation has required files
✓ Required streams available
✓ Output directory valid
✓ Output filename valid
✓ Settings compatible
```

If something is wrong:

```text
⚠ Cannot start operation

Episode 03.mkv has no subtitle track.

Select another file or change
the subtitle operation.
```

The Start button should become disabled when the operation is invalid.

---

# 20. Job execution architecture

The UI should never freeze during FFmpeg operations.

Architecture:

```text
UI
 │
 ▼
Operation Controller
 │
 ▼
Job Manager
 │
 ▼
Worker Thread / Process
 │
 ├── FFprobe
 ├── FFmpeg
 └── subtitle processing
 │
 ▼
Progress Signals
 │
 ▼
UI
```

For PySide6:

```text
Main Thread
     │
     ├── UI
     ├── Media Library
     └── Operation Settings
     
Worker
     │
     ├── FFmpeg
     ├── FFprobe
     └── processing
```

No long-running FFmpeg process should execute directly in the UI thread.

```python
│
├── operation
│
├── operation_selected_media_ids
│

│
├── jobs
│
└── workspace_status
```

```python
MediaItem

├── path
├── filename
├── size
├── duration
├── metadata
├── video_streams
├── audio_streams
├── subtitle_streams
```


# 26. Operation abstraction

Rather than putting every operation inside one giant UI class, define an operation interface.

```python
class MediaOperation:
    id: str
    name: str

    def build_input_widget(self):
        ...

    def build_settings_widget(self):
        ...

    def validate(self):
        ...

    def build_command(self):
        ...

    def estimate(self):
        ...
```

Then:

```text
ConvertOperation
JoinOperation
ConcatenateOperation
MergeSubtitlesOperation
MuxOperation
ExtractAudioOperation
ExtractSubtitlesOperation
TrimOperation
BurnSubtitlesOperation
```

Each operation owns its own:

```text
Input requirements
Settings
Validation
Command generation
Execution logic
```

The workspace doesn't need to know the details.

# 27. Dynamic operation system

When the user selects:

```text
Convert Media
```

Veyra does:

```text
operation = ConvertOperation

bottom-left
    ↓
ConvertMediaSelector

bottom-right
    ↓
ConvertSettings
```

When they select:

```text
Mux Media
```

Veyra swaps:

```text
bottom-left
    ↓
MuxMediaSelector

bottom-right
    ↓
MuxSettings
```

The rest of the application remains unchanged.

# 28. Media lifecycle

A media file moves through these states:

```text
DISCOVERED
    ↓
VALIDATING
    ↓
INSPECTING
    ↓
READY
    ↓
SELECTED
```

Potential failure:

```text
DISCOVERED
    ↓
INSPECTING
    ↓
FAILED
```

The library should show that visually:

```text
● Episode 01.mkv
  Ready

⚠ Episode 02.mkv
  Inspection failed

● Episode 03.mkv
  Ready
```

When adding media that is already in the workspace:


For folders containing duplicates, Veyra should not silently create duplicate entries.

# 32. Batch operations

Veyra is fundamentally designed around batch processing.

Example:

```text

```

```text

☑ Episode 04
☑ Episode 05
```

One operation produces multiple jobs.

```text
Operation
    ↓
Job 01
```

# 35. Settings architecture

Global Veyra settings should **not** clutter operation settings.

Global settings can contain:

```text
SETTINGS

General
├── Theme
├── Confirm destructive actions
└── Startup behavior

Processing
├── FFmpeg path
```

Operation-specific settings remain in the bottom-right workspace.

# 36. Output naming

Veyra should support templates rather than hard-coded names.

Example:

```text
{stem}.converted.{ext}
```

or:

```text
{stem}.en.srt
```

For joins:

```text
{first_stem}.complete.{ext}
```

This becomes especially useful for batch processing.

# 37. Hardware acceleration

Eventually the Convert/Burn settings can expose:

```text
ENCODER

Software
[ H.264 (libx264) ▼ ]

Hardware

[ NVIDIA NVENC ▼ ]

```

But only show available encoders based on actual FFmpeg capabilities.

Veyra should detect capabilities rather than presenting options that do not exist.

# 38. Intelligent controls

The UI should react to FFprobe information.

For example, if the selected media has:

```text
Video:
H.264
1920×1080
23.976 FPS
```

then Convert can default to:

```text
Resolution
[ Original ]

FPS
[ Original ]
```

If there are no subtitles:

```text
SUBTITLES

No subtitle streams detected.
```

If there are three subtitle tracks:

```text
SUBTITLES

☑ English
☐ Spanish
☐ French
```

If there is only one audio track, unnecessary track selection controls can be simplified.

# 39. Join intelligence

Join should inspect compatibility automatically.

For example:

```text
Episode 01
H.264 • 1080p • 23.976

Episode 02
H.264 • 1080p • 23.976

Episode 03
H.264 • 1080p • 23.976
```

Veyra can show:

```text
✓ Compatible video streams
✓ Compatible frame rate
✓ Compatible resolution
✓ Compatible container workflow
```

But if:

```text
Episode 03
H.265 • 720p • 25 FPS
```

show:

```text
⚠ Media streams differ

Episode 03 uses:
H.265
1280×720
25 FPS

Joining may require normalization/re-encoding.
```

# 40. Subtitle intelligence

For joining:

```text
Episode 01
English subtitles

Episode 02
English subtitles

Episode 03
English subtitles
```

Veyra automatically calculates:

```text
00:00:00
00:45:22
01:30:20
```

and merges them.

It should also validate subtitle ordering and language consistency.

# 41. UI state rules

These rules should be enforced:

### Adding media

```text
ADD MEDIA
→ adds to Media Library
→ inspects automatically
→ selects first newly added media
→ displays its information
```

### Clicking media

```text
CLICK MEDIA
→ changes current_media
→ updates top-right information
→ does NOT alter operation selection
```

### Changing operation

```text
CHANGE OPERATION
→ changes bottom-left operation input
→ changes bottom-right settings
→ preserves Media Library
→ operation-specific selection can reset or intelligently retain compatible files
```

### Selecting operation media

```text
SELECT MEDIA
→ affects only current operation
→ does NOT change current_media
```

### Running

```text
RUN
→ validates
→ creates jobs
→ starts worker
→ reports progress
→ produces results
```

```text
VEYRA

    │

    │   │

    │   │
```

## The golden rule

**Top = media management and inspection.**

**Bottom = operation management.**

**Left = selection/input.**

**Right = information/configuration.**

More specifically:

```text
┌──────────────────────┬─────────────────────────┐
│ MEDIA                │ INFORMATION             │
│                      │                         │
│ What media do I      │ Tell me about the       │
│ have?                │ media I clicked.        │
├──────────────────────┼─────────────────────────┤
│ OPERATION             │ CONFIGURATION            │
│                      │                         │
│ What do I want to    │ How should Veyra        │
│ do, and to which     │ perform it?             │
│ media?               │                         │
└──────────────────────┴─────────────────────────┘
```

That gives Veyra a **stable workspace architecture** where the UI doesn't need to be redesigned every time another FFmpeg/subtitle operation is added. The operation system becomes a pluggable layer on top of a single, persistent Media Library and FFprobe metadata model.
